### A 阶段高危服务操作专项：UI-12/13/23/24/36（当前批次验收需 CI 终态）

复核 `frontend/src/views/service/ServiceDetailView.vue` 时发现三类**可复现的实现风险**，归属既有服务详情/备用候选/资源绑定，不是新增功能：

- 重置凭证及新增白名单在弹窗确认后原来直接读取可变的路由服务ID，单页应用切到另一服务可能错写。现改为弹窗打开时固定服务ID/编号与详情加载版本，确认时验证对象和权限未变化，后端请求只使用被冻结的原服务ID；按钮 single-flight 防重复。新密钥仅在原服务仍为当前界面时显示，不在其他客户/服务弹窗泄露。
- 白名单停用原来没有明确影响确认，行ID也会与可变服务ID组合；现在冻结服务和行ID，用户二次确认后校验行仍 ACTIVE，取消不发送 DELETE，失败不假报已停用。
- 人工备用候选预检原来不能可靠隔离不同服务/后返回响应；现在按服务加载版本和预检请求版本防串单。503/网络失败显示未知，清除旧的切换影响结论。真实执行仍禁用，属于 B/C 设备能力，不把预检成功写作切换成功。
- 资源绑定关联独立 API 失败时不再兜底展示详情里可能过时的备用绑定表，必须错误可见。

本批新增四项 Chromium + Spring Boot/PostgreSQL（Mock产品执行器）专项案例：弹窗时跨服务切换的凭证重置拒绝、白名单新增拒绝、白名单停用取消不写入、人工切换预检失败不显示旧影响与执行。**只有新 PR 最终 head CI、主分支合并后 CI 实际通过，才计入自动化证据**。业务多角色人工授权、密钥轮换实际运营影响、候选真实网络切换仍未签署，Issue #8 不关闭。

### A1 订单确认、取消和付款核实操作签收增补（2026-10-16）

针对原台账的订单详情、付款核实和服务开通业务（客户→订单项→付款核实→模拟开通→实例关联），对 `frontend/src/views/service/OrderDetailView.vue` 实际审查发现：

- **业务动作的错单风险**：订单确认、取消、付款核实此前的全局弹窗在打开之后才取路由 `id` 发写请求。单页应用在弹窗期间切换订单，可能把原单操作提交给后来查看的订单。现已冻结 `orderId`、订单编号、状态、付款状态与加载版本，确认后验证仍为当前有效订单且具有对应权限；写请求只使用被冻结的订单 ID。
- **付款二段式核实**：先核对付款凭证号、再填写核实渠道与依据。任一弹窗前后订单、状态、权限、数据加载代数发生变化均拒绝付款确认；确认全过程锁定单次操作，避免重复提交。取消不会写入付款凭证。
- **失败语义**：确认订单、取消和核款接口失败时明确说明“未确认成功、先回查审计”，不会在服务开通页面或付款凭证栏伪报已到账；核实到账仅是人工管理凭证，不代表支付网关收款、供应商采购或真实网络交付成功。
- **专项浏览器回归（新增四项）**：订单取消弹窗跨单、付款凭证第一步跨单、付款核实第二步跨单、订单确认弹窗跨单，均要求 **无错误订单 POST**。原有 A1 的客户订单跳转、订单明细与实际服务、未付款不得开通、Mock 交付边界等仍完整回归；本批须以最终 PR + 合并后的 `main` CI 为实际验收证据。
- **仍未签收**：实际用户进行完整收款凭证真实性核对、订单授权职责分离、变更审计全流程与多角色人工签字。不会因自动化全部通过就关闭 Issue #8。

### A1 订单开通后持久关系与向导跨单复核（PR #31 已合并验证）

- **订单开通向导 SPA 切单**：此前只在页面首次挂载时读取 `?orderId=`，同一 Vue 实例切换订单时可能沿用前一单付款、预检、交付配置及结果；现以当前路由订单号为唯一数据源，切单立即清空旧快照，并通过预检请求版本阻断旧订单异步回填。
- **开通提交与结果归属**：确认时冻结订单号、开通原因和各订单项的交付计划；请求返回时若用户已切单，只提示回原订单核查，不得把旧开通结果、新密钥或成功消息展示在新订单页面。后端仍需最终核对付款、资格及并发资源；请求失败不能直接断言数据库无记录，提示先回查再重试。
- **持久服务关系独立回查**：开通结果页在一次性回执之外额外读取 `GET /relations/orders/{orderId}/services`，比对返回的服务ID与实际订单服务关联。请求失败显示未知，缺失或截断显示差异警告。服务明细入口可逐项核对资源绑定、出口授权与执行任务。**管理面持久记录一致不等于代理网络已真实交付**。
- **本批已通过的代码与浏览器证据**：[PR #31](https://github.com/sunkai-hit/IP-proxy-platform/pull/31) 的最终 head [CI #38874415884](https://github.com/sunkai-hit/IP-proxy-platform/actions/runs/38874415884) 三项成功、78/78 Chromium 通过（其中本批新增4项）：一个基于真实 PostgreSQL 的只读订单→三条服务→服务订单主档→资源绑定接口→操作任务回查，以及三项管理面浏览器回归：同页切单付款差异、慢响应隔离、模拟管理回执后持久关联失败/重试。模拟回执测试不真正调用开通写入。
- **验收边界**：当前 CI 不能替代全部订单、资源与后台审计表逐字段、多角色、真实付款凭证的人为签署。B/C 五种产品实网交付、真实设备动作仍暂缓。

### A1 订单核款—模拟开通—审计记录反查（PR #32 已合并，PR CI 通过）

- **已确认的真实持久事件**：付款人工核实写入 `sys_operation_log` 的 `object_type=BIZ_ORDER`、`operation=PAYMENT_RECEIPT_CONFIRMED`；V1.3 新购订单模拟开通写入 `object_type=ORDER`、`operation=PROVISION_V12`。两者对象 ID 均为业务订单 ID，但之前操作审计视图仅为 `SERVICE` 生成详情链接，导致 A1 付款和开通审计与订单详情脱节。
- **本轮修复**：`GET /runtime-logs/v12/operation` 将纯数字的 `ORDER` 和 `BIZ_ORDER` 统一生成 `/orders/{id}`，保留原始类型与事件名及审计脱敏来源；日志中心按目标业务页面实际路由权限（`order:read`、`service:read` 等）控制“查看”入口，未知路径不导航。不能通过仅有日志权限绕过订单业务详情权限。
- **实际验证证据**：[PR #32](https://github.com/sunkai-hit/IP-proxy-platform/pull/32) 已合并；最终 head `4ab59e653ba163bb7ba847b3942fca9b87a5528a` 的 [CI #38877040271](https://github.com/sunkai-hit/IP-proxy-platform/actions/runs/38877040271) 79/79 Chromium、前端/后端/Docker 3/3 通过。测试从真实 PostgreSQL 的双订单项/三服务业务闭环按原订单 ID 读取 PAYMENT_RECEIPT_CONFIRMED 与 PROVISION_V12 两类脱敏审计，核验 SUCCESS、订单详情跳转及三条服务关联；只读角色直调操作审计 API 返回 AUTH_FORBIDDEN。合并后的 `main` 完整 CI 需以独立 Actions 结果确认。
