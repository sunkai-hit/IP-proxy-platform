# IP代理管理平台 M1–M8 开发过程汇总

> 文档性质：研发过程基线与里程碑纪要  
> 覆盖范围：M1「工程骨架」至 M8「监控 + 告警 + 数据统计」  
> 汇总时间：2026-08-30  
> 说明：本文根据 M1–M8 各阶段完成后的阶段总结、已冻结技术基线以及当前 GitHub 仓库实际实现进行整理。部分较早阶段的原始对话总结未能完整逐字恢复，因此本文采用“阶段汇总”的方式保留当时已经明确的实现结论、关键设计决策、验收结果与未实现边界，不将无法确认的内容补写为既成事实。

## 一、项目从 M1 到 M8 的总体演进

M1–M8 的建设不是按“先做页面、后补后端”的方式推进，而是围绕已经确认的业务主链逐步形成一个可以真实运行、真实联调、真实验收的管理平台。

核心业务主链逐步演进为：

```text
客户
  ↓
客户账号 / 认证
  ↓
产品 + 套餐 + 资源策略
  ↓
订单 → 订单项
  ↓
服务实例
  ↓
资源绑定 + 服务凭证
  ↓
Open Token
  ↓
IP提取 / 白名单
  ↓
运行日志
  ↓
监控采集
  ↓
告警触发 / 处理 / 恢复
  ↓
小时统计
  ↓
首页 / 监控 / 告警 / 统计
```

与此同时，资源侧形成了另一条持续贯穿各阶段的主链：

```text
真实运维API / 外部供应商API
          ↓
      Adapter层
          ↓
CentOS → ROS → 家宽/线路 → IP
          ↓
      统一资源池
          ↓
      产品资源策略
          ↓
       服务实例
          ↓
Open API / Proxy / VPN / Tunnel 数据面
```

到 M8 完成时，平台已经基本形成三类闭环：

1. **核心管理闭环**：客户 → 产品 → 订单 → 服务 → 资源；
2. **客户调用闭环**：客户账号 → Token → IP提取/白名单 → 运行日志；
3. **运行保障闭环**：监控 → 告警 → 通知 → 恢复 → 统计 → 工作台。

# 二、M1「工程骨架」

## 2.1 阶段目标

M1 的目标不是实现完整业务，而是把已经确认的静态原型升级为一套真正可持续开发的前后端工程，并验证技术栈、数据库迁移、登录、安全、前后端联调和 CI 能够正常工作。

## 2.2 技术栈正式落地

### 前端

```text
Vue 3
TypeScript
Vite
Element Plus
Pinia
Vue Router
Axios
ECharts
```

### 后端

```text
Java 21
Spring Boot 4.1.1
Spring MVC
Spring Security
JWT
MyBatis
Maven
```

### 基础设施

```text
PostgreSQL
Redis
Flyway
Docker / Docker Compose
OpenAPI / Swagger
Spring Boot Actuator
Micrometer
```

架构上明确采用：

```text
前后端分离
+
模块化单体
```

而没有在项目初期引入微服务、Kafka、Elasticsearch、ClickHouse 等复杂基础设施。

## 2.3 仓库结构调整

原有静态原型被保留，作为产品和视觉基准，而不是直接删除。

```text
IP-proxy-platform/
├── prototype/         # 原静态原型
├── frontend/          # Vue工程
├── backend/           # Spring Boot工程
├── database/
├── docs/
├── deploy/
├── docker-compose.yml
└── README.md
```

这一步的重要意义是：后续正式页面和业务功能可以不断重构，但 `prototype/` 始终保留为已确认需求和视觉参考。

## 2.4 后端基础能力

M1 建立了：

- Spring Boot 应用骨架；
- PostgreSQL 数据源；
- Redis；
- Flyway 数据库迁移；
- JWT 登录；
- 统一 API 返回结构；
- 全局异常处理；
- Request ID；
- Swagger；
- Actuator 健康检查；
- 基础安全配置。

统一 Admin API 返回模型确定为：

```json
{
  "code": "0",
  "message": "success",
  "data": {},
  "requestId": "req_xxxxxx",
  "timestamp": 0
}
```

## 2.5 前端首次真实联调

M1 完成了真正的：

- 登录页；
- JWT 保存；
- 后台 Layout；
- 路由框架；
- Dashboard；
- 前后端接口调用。

首页最初主要用于验证数据库、Redis、用户与客户表是否真正连通，而不是展示 Mock 数据。

## 2.6 数据库

M1 建立并验证了 Flyway **V1–V5** 基础迁移。

这一阶段的主要价值是证明：

```text
空数据库
  ↓
Flyway执行
  ↓
数据库结构完整建立
  ↓
Spring Boot正常启动
```

## 2.7 M1 验收

M1 完成时已经验证：

- 前端构建成功；
- 后端 Maven 构建成功；
- PostgreSQL 正常；
- Redis 正常；
- Flyway V1–V5 可在空库执行；
- JWT 登录可用；
- Dashboard 前后端真实联调成功；
- GitHub CI 通过。

## 2.8 M1 明确边界

M1 仍然是工程基础阶段，因此：

- 绝大多数业务页面仍只是路由或基础占位；
- 尚未形成完整客户、资源、产品、订单、服务业务能力；
- CI 重点验证工程和接口，而不是完整业务链；
- 不因为原型已经存在，就把静态 Mock 当成正式业务实现。

# 三、M2「系统基础能力」

## 3.1 阶段目标

M2 的目标是把后台系统的“用户、角色、权限、字典、参数、日志”等公共底座先做实，使后续 M3–M8 所有业务模块都能够基于真实权限体系运行。

## 3.2 系统管理能力

M2 正式实现：

```text
用户管理
角色管理
权限管理
字典管理
参数配置
登录日志
操作审计
```

前端“系统管理”从占位页升级为真实业务页面。

## 3.3 RBAC 权限体系

正式采用：

```text
用户 N:M 角色
角色 N:M 权限
```

核心表包括：

```text
sys_user
sys_role
sys_permission
sys_user_role
sys_role_permission
```

JWT 中开始携带：

- 用户信息；
- 角色；
- 权限编码。

权限检查同时存在于：

```text
前端路由/按钮
+
后端接口
```

避免只依赖前端隐藏按钮作为安全控制。

## 3.4 权限与字典的边界

这一阶段进一步明确：

### 可以后台配置的字典

例如：

- 客户类型；
- 运营商；
- 代理协议；
- 认证方式；
- 接入方式；
- 资源来源；
- 通知方式。

### 不能任意新增的核心状态

例如：

- OrderStatus；
- ServiceStatus；
- AlarmStatus；
- ExclusiveAllocationStatus。

这些状态直接参与业务状态机，因此必须由 Java Enum / 状态机控制，不能让管理员随意新增一个状态后破坏业务逻辑。

## 3.5 安全保护

M2 增加了针对后台自身的防误操作规则，例如：

- SUPER_ADMIN 保护；
- 当前登录账号保护；
- 敏感系统参数脱敏；
- 高影响操作进入操作审计。

## 3.6 数据库

新增 Flyway：

```text
V6__system_foundation.sql
```

V1–V6 形成系统公共底座。

## 3.7 M2 验收

M2 CI 验证了：

- 前端构建；
- 后端构建；
- Flyway V1–V6；
- 登录；
- JWT 权限；
- 系统管理接口；
- 用户/角色/权限等真实 CRUD；
- 权限拦截；
- 操作审计。

至此，后续业务模块不再各自实现登录和权限，而是全部建立在 M2 之上。

# 四、M3「客户管理」

## 4.1 阶段目标

M3 开始进入正式业务模块，目标是建立统一“客户”对象，并使客户、认证、账号、服务引用、凭证引用和使用情况可以在同一客户视角中查看。

## 4.2 客户档案

实现：

- 客户列表；
- 分页；
- 条件筛选；
- 新增；
- 编辑；
- 详情；
- 客户状态流转。

客户成为订单、服务和 Open API 的统一主体。

## 4.3 客户认证

支持：

```text
个人认证
企业认证
```

认证资料采用可扩展结构保存，并实现：

```text
提交
→ 审核
→ 通过 / 驳回
```

认证状态与客户档案形成关联，而不是混在一个简单字段中完成全部逻辑。

## 4.4 客户账号

客户账号正式成为客户访问后续 Open API 的基础身份。

实现：

- 创建账号；
- BCrypt 密码；
- 密码重置；
- 冻结；
- 恢复；
- 停用；
- 账号状态管理。

## 4.5 客户详情聚合

客户详情不只显示基本资料，同时开始聚合：

- 客户认证；
- 客户账号；
- 服务引用；
- 服务凭证引用；
- 使用概览。

M3 由此建立了后续所有客户运营视角的基础。

## 4.6 服务认证信息保护

服务 Token、密钥、密码等敏感信息不是普通客户详情字段。

M3 明确增加独立权限，例如：

```text
customer:credential:read
```

历史查询默认只显示类似：

```text
tk_8ac4••••••a91d
```

而不是返回完整密钥。

## 4.7 数据库

新增：

```text
V7__customer_management.sql
```

## 4.8 API 与前端

M3 建立了独立的客户管理 API 契约，并将客户页从静态原型升级为 Vue 真实页面。

对应接口文档：

```text
docs/api/openapi-customer-m3.yaml
```

## 4.9 M3 验收

CI 在全新 PostgreSQL 中验证：

- V1–V7 全部迁移；
- 客户新增/编辑/查询；
- 客户认证提交与审核；
- 客户账号创建与状态变化；
- 密码处理；
- 权限；
- 审计；
- 前端构建；
- 后端构建；
- 完整客户生命周期 Smoke Test。

## 4.10 M3 明确没有合并的运营反馈

M3 主线没有把后续“运营端反馈分支”直接混入客户核心模型。

当时明确暂不纳入：

- 余额；
- 折扣；
- 客户来源；
- 专属注册链接；
- 手工充值；
- 退款；
- 财务相关能力。

这部分继续作为独立运营反馈分支保留。

# 五、M4「资源管理」

## 5.1 阶段目标

M4 的目标是把原先需求中的“CentOS、ROS、家宽、线路、IP、外部资源”等概念真正变成统一资源模型，并且严格区分：

```text
平台同步/查看能力
≠
真实运维控制能力
```

## 5.2 资源拓扑正式落地

资源关系确定为：

```text
CentOS
  ↓ 1:N
ROS
  ↓ 1:N
家宽 / 线路
  ↓ 1:N（随时间变化）
IP
```

产品层的“短效/长效”不再作为底层 IP 资源类型。

也就是说：

```text
短效 / 长效
= 产品/服务策略
≠ IP物理属性
```

## 5.3 基础资源同步

CentOS、ROS、线路、IP 采用同步方式管理。

核心原则：

```text
上游API
   ↓
ResourceAdapter
   ↓
标准化
   ↓
平台资源表
```

正式环境中，如果没有配置真实上游 Adapter，系统会明确返回上游适配器未配置，而不会产生假资源。

## 5.4 ResourceAdapter

M4 建立：

```text
ResourceAdapter
├── NoopResourceAdapter
└── MockResourceAdapter
```

其中：

- `NoopResourceAdapter` 用于没有真实接口配置时的正式边界；
- `MockResourceAdapter` 仅用于 CI / 本地联调。

这一结构为后续真正接入 ROS、CentOS 或供应商接口留出稳定扩展点。

## 5.5 基础资源不伪造“管理”能力

M4 非常明确地限制了基础资源操作范围。

CentOS / ROS / 线路 / IP 当前主要支持：

- 同步；
- 列表；
- 查询；
- 详情；
- 状态展示。

没有在接口未确认时自行实现：

- 新增上游 CentOS；
- 编辑真实 ROS；
- 删除真实线路；
- 远程重拨；
- 重启 ROS；
- 切换出口；
- 远程执行脚本；
- 其他未经确认的真实网络控制。

## 5.6 统一资源池

正式建立：

```text
res_pool
res_pool_ip
```

IP 与资源池采用 N:M：

```text
IP ↔ 多个逻辑资源池
```

而不是在 `res_ip` 上直接放一个单一 `pool_id`。

这样可以同时表达：

- 山东联通池；
- 华东优质池；
- VIP 候选池；
- 其他交叉逻辑池。

## 5.7 自有与外部资源统一

外部供应商 IP 经过：

```text
Supplier / Adapter
      ↓
获取
      ↓
标准化
      ↓
检测
      ↓
去重
      ↓
res_ip
      ↓
资源池
```

所以外部 IP 并没有另建一套完全独立的客户使用模型。

## 5.8 独享资源

独享资源单独维护占用关系：

```text
res_exclusive_allocation
```

核心规则：

```text
同一资源同一时刻最多存在一个有效独享占用
```

释放后进入：

```text
PENDING_RECYCLE
```

等待回收/重新检测，而不是简单删除关系后立刻宣称资源可再次使用。

## 5.9 域名配置

M4 实现平台域名配置与目标 IP 关系。

但刷新动作只更新平台中的目标状态并进入：

```text
PENDING_UPDATE
```

没有在真实 DNS 接口未确认时宣称已经完成外部 DNS 修改。

## 5.10 外部供应商与同步任务

实现：

- 外部供应商；
- 供应商状态；
- 外部资源接入；
- 同步任务；
- 同步结果；
- 重试能力；
- 相应权限。

## 5.11 前端

资源管理形成约 10 个主要入口：

```text
资源概览
CentOS
ROS
线路
IP
资源池
独享资源
域名配置
供应商
外部资源/同步任务
```

## 5.12 数据库

新增：

```text
V8__resource_management.sql
```

## 5.13 M4 验收

M4 完成时：

- Vue 页面完成；
- 后端 API 完成；
- V1–V8 空库迁移成功；
- Mock Adapter 可完成 CI 资源同步；
- 资源池可重新计算成员；
- 自有 IP 可以进入统一资源池；
- CI 全通过。

# 六、M5「产品管理」

## 6.1 阶段目标

M5 的目标是把“短效IP、长效IP、独享IP、VPN、隧道”正式建成五类客户产品，同时确保产品配置与底层资源保持解耦。

产品层最终采用：

```text
产品
+
类型专项配置
+
套餐
+
资源策略
```

## 6.2 五类产品

正式支持：

```text
SHORT_IP      短效IP
LONG_IP       长效IP
EXCLUSIVE_IP  独享IP
VPN            VPN
TUNNEL         隧道
```

## 6.3 通用配置

产品通用配置包括：

- 接入方式；
- 代理协议；
- 认证方式；
- 资源模式；
- 地区；
- 运营商；
- 产品状态；
- 其他共性能力。

## 6.4 五类专项配置

### 短效 IP

主要包括：

- IP 有效时间；
- 单次提取上限；
- 提取频率限制；
- 去重周期；
- IP 切换策略。

### 长效 IP

主要包括：

- 保持周期；
- IP / 线路绑定；
- 自动替换；
- 故障阈值；
- 主备/故障切换。

### 独享 IP

主要包括：

- 独享资源类型（IP / LINE）；
- 默认资源数量；
- 锁定超时；
- 替换规则；
- 释放规则。

### VPN

主要包括：

- VPN 协议；
- 凭证类型；
- 设备数；
- 连接数；
- 出口相关规则。

### 隧道

主要包括：

- 入口域名 / Host；
- 入口端口；
- 会话保持；
- 并发限制；
- IP 切换相关规则。

## 6.5 套餐

产品与套餐采用 1:N。

套餐主要定义：

- 服务有效期；
- IP 数量；
- 提取额度；
- 流量额度；
- 并发额度；
- 设备额度；
- 白名单额度；
- 改 IP 次数；
- 价格；
- 状态。

产品负责“能力”，套餐负责“卖多少、卖多久、限制多少”。

## 6.6 产品资源策略

M5 资源策略直接引用 M4 的统一资源池。

```text
Product
  ↓
ResourceStrategy
  ↓
多个 ResourcePool
```

资源策略支持：

- 调度方式；
- 资源来源优先级；
- 地区；
- 运营商；
- 多资源池优先级；
- 故障转移；
- IP 保持；
- 切换规则。

## 6.7 启用规则

产品不是创建后即可直接对外提供服务。

启用前必须检查：

- 产品专项配置是否完整；
- 产品类型与配置是否匹配；
- 是否存在有效资源策略；
- 资源策略验证是否通过。

资源策略必须先验证通过才能启用。

## 6.8 停用边界

产品停用的基本原则是：

```text
禁止新订单 / 新服务
```

但不会简单把所有已经生效的历史服务一并终止。

## 6.9 复制规则

产品复制明确采用：

```text
复制：产品 + 类型专项配置
不复制：套餐 + 资源策略
```

# 七、M6「订单与服务管理」

## 7.1 阶段目标

M6 是整个业务模型真正开始闭环的阶段。

前面 M3 建立客户，M4 建立资源，M5 建立产品；M6 的任务是将这些对象通过订单和服务实例真正连接起来。

## 7.2 订单与服务实例彻底分开

M6 没有采用“订单就是服务”的简化设计。

正式模型：

```text
biz_order
   ↓ 1:N
biz_order_item
   ↓
svc_instance
```

一个订单可以包含多个产品项，一个订单项也可以产生一个或多个服务实例。

## 7.3 订单模型

订单用于记录商业购买关系。

状态包括：

```text
待确认
→ 待开通
→ 已开通
→ 已完成
```

未开通订单允许取消。

订单本身**不直接占用资源**。

只有真正进入服务开通流程时，才会执行：

```text
资源选择
→ 资源锁定
→ 服务实例
→ 凭证
```

## 7.4 服务实例成为核心运行对象

M6 进一步确认：

```text
ServiceInstance
=
客户
+ 产品
+ 套餐
+ 资源策略
+ 实际资源
+ 认证凭证
+ 生命周期
```

服务实例也是后续：

- Open API；
- 监控；
- 日志；
- 告警；
- 统计；

共同引用的核心业务对象。

## 7.5 快照机制

服务开通时固化：

```text
product_snapshot
package_snapshot
strategy_snapshot
quota_snapshot
```

这样产品、套餐或策略以后即使修改，也不会改写历史客户购买时的服务口径。

## 7.6 服务开通流程

服务开通不是一条普通 INSERT。

完整逻辑为：

```text
校验客户
  ↓
校验订单 / 订单项
  ↓
读取产品 / 套餐
  ↓
读取资源策略
  ↓
检查资源容量
  ↓
选择 / 锁定资源
  ↓
创建服务实例
  ↓
创建资源绑定
  ↓
生成凭证
  ↓
更新订单
  ↓
写审计
  ↓
调用数据面 Adapter（如适用）
```

## 7.7 资源绑定

服务不把所有资源 ID 直接塞进 `svc_instance`。

使用：

```text
svc_resource_binding
```

支持不同资源类型：

```text
POOL
CENTOS
ROS
LINE
IP
DOMAIN
SUPPLIER
```

并支持 PRIMARY / BACKUP / ENTRY / OUTBOUND 等绑定角色。

## 7.8 共享与独享服务

共享资源服务主要绑定资源池。

独享 IP 服务除资源池外，还会：

- 选择具体 IP；
- 创建独享锁定；
- 创建 `res_exclusive_allocation`；
- 记录客户/服务占用关系。

## 7.9 服务凭证

M6 正式建立：

```text
svc_credential
```

支持：

- Token；
- 用户名密码；
- VPN 私钥；
- VPN 证书；
- 隧道账号。

核心安全规则：

```text
完整新密钥
仅在创建 / 重置响应中返回一次
```

历史查询只保留：

```text
secret_mask
```

## 7.10 白名单

服务实例支持：

```text
svc_whitelist
```

并具备新增、查询、停用等能力。

## 7.11 服务生命周期

实现：

```text
PENDING
ACTIVE
SUSPENDED
EXPIRED
TERMINATED
PROVISION_FAILED
```

管理动作包括：

- 暂停；
- 恢复；
- 续费；
- 凭证重置；
- 终止；
- 资源释放。

## 7.12 终止和释放

终止服务时：

```text
撤销凭证
  ↓
解除资源绑定
  ↓
生成 svc_release_record
  ↓
独享资源进入 PENDING_RECYCLE
```

不会直接删除历史服务。

## 7.13 ServiceProvisionAdapter

M6 建立：

```text
ServiceProvisionAdapter
```

用于隔离未来真正的：

- Proxy Gateway；
- VPN；
- Tunnel；
- ROS；
- 其他数据面配置。

真实数据面协议没有确认时，不把 Spring Boot 普通业务接口伪装成代理流量转发层。

## 7.14 数据库

新增：

```text
V10__order_service_management.sql
```

## 7.15 API / 前端

对应接口契约：

```text
docs/api/openapi-order-service-m6.yaml
```

前端正式进入订单与服务实例管理，不再只是静态 Tab。

## 7.16 M6 验收

M6 验证了：

- 多订单项；
- 订单确认；
- 服务开通；
- 服务实例生成；
- 产品/套餐/策略快照；
- 共享资源池绑定；
- 独享 IP 锁定；
- 服务凭证；
- 暂停/恢复；
- 服务终止；
- 资源释放；
- V1–V10 Flyway；
- 前后端构建。

M6 完成之后，M3–M5 不再是孤立模块，平台首次形成了完整的核心业务管理闭环。

# 八、M7「Open API + 运行日志体系」

## 8.1 阶段目标

M7 的核心目标是让“已经开通的服务实例”真正具备客户调用入口，并建立客户调用后的可追溯日志。

调用路径确定为：

```text
客户账号用户名 + 密码
        ↓
POST /api/open/v1/auth/token
        ↓
      Open Token
        ↓
IP提取 / 白名单
```

## 8.2 Open API 命名空间

客户接口独立于后台 Admin API：

```text
/api/open/v1/*
```

主要接口：

```text
POST   /api/open/v1/auth/token
GET    /api/open/v1/proxy/extract
GET    /api/open/v1/whitelist
POST   /api/open/v1/whitelist
DELETE /api/open/v1/whitelist/{ip}
```

## 8.3 Token 与服务实例绑定

Open Token 不是一个脱离业务的独立账号。

正式链路：

```text
customer_account
      ↓
open_access_grant
      ↓
svc_instance
```

每次调用都会实时检查：

- 客户是否 ACTIVE；
- 客户账号是否 ACTIVE；
- 服务是否 ACTIVE；
- 服务是否已经生效；
- 服务是否过期；
- 产品接入方式是否为 API_EXTRACT。

因此服务暂停、终止或到期时，Open API 会同步失效。

## 8.4 Token 不明文落库

M7 使用类似：

```text
oa.<grantId>.<tokenVersion>.<HMAC-signature>
```

完整 Open Token 不存入数据库明文。

同时支持：

```text
changeToken=false
→ 同一版本继续返回稳定Token

changeToken=true
→ token_version + 1
→ 返回新Token
→ 旧Token立即失效
```

## 8.5 多服务歧义处理

如果一个客户账号同时存在多个满足条件的 API_EXTRACT 服务，当前接口不会擅自猜应该使用哪一个服务。

返回：

```text
OPEN_SERVICE_AMBIGUOUS
```

在客户侧“服务选择协议”没有确认前，没有自行加入未经确认的 serviceId/productId 参数规则。

## 8.6 IP 提取

提取接口真正沿用 M4–M6 已建立的资源和服务关系：

```text
Open Token
   ↓
服务实例
   ↓
服务固化策略
   ↓
服务资源绑定
   ↓
统一资源池
   ↓
可用 res_ip
   ↓
返回客户
```

校验包括：

- 单次提取上限；
- 套餐总额度；
- 频率限制；
- 资源池状态；
- IP 可用状态；
- 重复 IP；
- 地区；
- 运营商；
- 去重周期。

M7 没有绕过 M4/M5/M6 直接从 IP 表随机返回数据。

## 8.7 白名单

白名单接口直接操作服务实例白名单：

- 查询；
- 新增；
- 停用/删除调用关系。

## 8.8 Request ID 与日志追踪

一次 IP 提取会真正写入：

```text
log_ip_extract
+
log_api
```

两类日志通过同一个 `requestId` 关联。

可以追踪：

- 客户；
- 客户账号；
- 服务实例；
- 产品；
- 请求条件；
- 客户端 IP；
- 返回数量；
- 错误码；
- 接口耗时。

## 8.9 失败请求也保留日志

一个关键实现是：

```text
失败日志使用独立 REQUIRES_NEW 事务
```

因此即使主业务事务因为：

- Token 无效；
- 服务暂停；
- 额度不足；
- 资源不可用；

发生回滚，失败调用日志仍然能够保留下来。

## 8.10 运行日志后台

后台新增“运行日志”页面和权限：

```text
runtime-log:access
runtime-log:extract:read
runtime-log:api:read
runtime-log:usage:read
```

页面包括：

```text
IP提取日志
API日志
使用日志
```

## 8.11 “提取 IP”不等于“使用 IP”

M7 明确没有把提取接口调用伪装成真实代理流量。

定义：

```text
log_ip_extract
→ 客户提取IP

log_usage
→ 客户真实代理请求
```

真实 `log_usage` 应来自：

- Proxy Gateway；
- VPN；
- Tunnel；
- ROS；
- 其他真实数据面。

因此 M7 只实现 `log_usage` 后台查询结构，真实写入等待数据面回传协议确认。

## 8.12 数据库

新增：

```text
V11__open_api_runtime_logs.sql
```

## 8.13 API 文档

新增：

```text
docs/api/openapi-open-v1.yaml
docs/api/openapi-runtime-log-m7.yaml
```

## 8.14 M7 验收

M7 完成时：

- 前后端构建成功；
- V1–V11 全量迁移成功；
- 客户账号可换取 Token；
- `changeToken=false` 稳定；
- `changeToken=true` 后旧 Token 失效；

- 白名单增删查成功；
- 服务暂停后 Open Token 实时失效；
- `requestId` 可关联提取日志与 API 日志；
- 失败 API 调用可以保留日志；
- `log_usage` 保持为 0，未伪造代理使用数据；
- GitHub CI 全绿。

# 九、M8「监控 + 告警 + 数据统计」

## 9.1 阶段目标

M8 的目标是在已经真实运行的 M3–M7 业务链上增加运行保障能力，使平台能够回答：

```text
资源现在是否正常？
服务现在是否正常？
数据是不是过期了？
什么情况应该告警？
告警有没有重复刷屏？
谁处理了？
什么时候恢复？
有没有通知？
客户/产品/资源最近用了多少？
```

## 9.2 统一监控对象

监控后端统一覆盖：

```text
CENTOS
ROS
LINE
IP
POOL
SUPPLIER
SERVICE
```

前端主要呈现六类运行监控页签：

```text
CentOS监控
ROS监控
线路监控
IP资源监控
外部资源监控
服务运行监控
```

资源池作为后端统一监控对象参与健康判断、统计和告警。

## 9.3 监控数据模型

当前状态：

```text
mon_object_status
```

时序样本：

```text
mon_metric_sample
```

每轮采集记录：

```text
mon_collect_run
```

监控页面支持：

- 状态汇总；
- 对象查询；
- 健康/异常/未知；
- 指标趋势；
- 手工采集。

## 9.4 数据过期不等于健康

默认过期时间：

```text
300秒
```

如果上游状态长时间没有更新：

```text
ONLINE
  ↓ 数据过期
UNKNOWN
```

而不是继续显示为绿色 ONLINE。

同时区分：

### 外部/上游采集型状态

```text
CentOS / ROS / LINE / IP / SUPPLIER
```

会根据上游时间判断过期。

### 平台自身业务状态

```text
SERVICE / POOL
```

不会因为业务记录 `updated_at` 超过 5 分钟就被误判为未知。

但它们的**监控采集结果本身**长时间未刷新时，页面仍可按监控采集时间判断为 stale。

## 9.5 MonitorProbeAdapter

M8 建立：

```text
MonitorProbeAdapter
```

正式环境默认：

```text
NoopMonitorProbeAdapter
```

没有真实 ROS / 线路探测 / 主机监控接口时，不自动制造 CPU、延迟等假指标。

CI / 本地联调使用：

```text
m8-mock
```

用于可重复验证告警链。

## 9.6 告警规则

支持对象：

```text
CENTOS / ROS / LINE / IP / POOL / SUPPLIER / SERVICE
```

支持运算符：

```text
EQ / NE / GT / GTE / LT / LTE / IN / NOT_IN
```

告警级别：

```text
INFO / MINOR / MAJOR / CRITICAL
```

支持：

- 阈值；
- 连续命中次数；
- 持续时间；
- 恢复通知；
- 重复通知间隔；
- 启用/停用；
- 新增/编辑/删除规则。

## 9.7 告警去重

同一个：

```text
规则 + 对象 + 指标
```

只允许存在一条活动告警。

重复异常时：

```text
不新建告警
occurrence_count + 1
last_triggered_at 更新
```

V12 同时增加数据库活动告警唯一约束，避免并发采集下出现重复活动事件。

## 9.8 告警生命周期

正式实现：

```text
OPEN
 ↓
ACKNOWLEDGED
 ↓
PROCESSING
 ↓
RECOVERED
 ↓
CLOSED
```

过程写入：

```text
alarm_process_record
```

因此可以审计：

- 谁确认；
- 谁开始处理；
- 处理备注；
- 何时恢复；
- 何时关闭。

## 9.9 自动恢复

M8 CI 使用真实业务链构造了一条线路延迟规则：

```text
对象：LINE
指标：ACTIVE_PROBE_LATENCY_MS
条件：> 40ms
级别：MAJOR
```

Mock 第二条线路产生：

```text
46ms
```

验收过程：

```text
第一次采集
→ 触发1条告警

确认
→ ACKNOWLEDGED

开始处理
→ PROCESSING

第二次采集
→ 仍异常
→ 不新增告警
→ occurrence_count + 1

规则阈值修改为100ms

第三次采集
→ 46 < 100
→ 自动 RECOVERED
→ 写恢复处理记录
→ 发送恢复通知
```

这证明告警不是只实现了列表 CRUD，而是真正进入监控采集链。

## 9.10 通知体系

支持：

```text
PLATFORM
DINGTALK
WEBHOOK
```

```text
alarm_notification
```

记录：

- 通知通道；
- 目标；
- 消息快照；
- 发送结果；
- 错误信息；
- 发送时间。

钉钉通过环境变量：

```text
DINGTALK_WEBHOOK_URL
```

接入。

未配置钉钉时明确记录发送失败，不伪造成功。

通用 WEBHOOK 当前只保留模型和边界，因为目标地址、签名、鉴权方式尚未正式确认。

## 9.11 数据统计

```text

```

```text

stat_customer_usage_hourly
stat_product_service_hourly
stat_supplier_hourly
```

```text

```

### 基础资源统计

- CentOS 总数/在线；
- ROS 总数/在线；
- 线路总数/在线/异常。

### IP 统计

- IP 总量；

### 客户使用统计

### 产品与服务统计

### 外部资源统计

- 可用 IP；

# 十、M1–M8 过程中形成的关键工程原则

## 10.1 管理面与数据面分离

Spring Boot 是管理面，负责：

- 客户；
- 产品；
- 资源；
- 订单；
- 服务；
- 凭证；
- Open API 权限；
- 监控；
- 日志；
- 告警；
- 统计。

真正高吞吐代理流量的数据面不通过普通 Spring MVC 请求转发：

```text
客户
 ↓
Proxy / Tunnel / VPN Gateway
 ↓
ROS / 家宽
 ↓
Internet
```

Spring Boot 只负责配置、调度、授权、查询和观测。

## 10.2 Adapter 优先

凡是还没有确认真实外部协议的部分，都通过 Adapter 隔离。

目前已经形成：

```text
ResourceAdapter
ServiceProvisionAdapter
MonitorProbeAdapter
```

原则始终是：

```text
接口没确认
→ 保留抽象
→ 不伪造真实能力
```

## 10.3 资源与产品解耦

底层资源不直接区分短效/长效。

```text
IP / LINE / ROS / Pool
= 基础资源

短效 / 长效 / 独享 / VPN / 隧道
= 产品和服务规则
```

## 10.4 订单与服务分离

订单描述购买关系，服务实例描述真正可用的运行服务。

这是 M6 以后所有 Open API、资源绑定、凭证、监控、日志和统计能够自然关联的基础。

## 10.5 历史快照不可被当前配置覆盖

服务开通时保存：

```text
产品快照
套餐快照
资源策略快照
权益快照
```

当前配置改变，不改变历史服务口径。

## 10.6 核心状态由代码控制

字典可以配置展示型、枚举型业务项；但订单、服务、告警、独享占用等核心状态必须由状态机控制。

## 10.7 敏感信息不明文保存/展示

包括：

- 密码；
- Open Token；
- VPN 私钥；
- 供应商密钥；
- Webhook；
- 服务密钥。

采用 Hash / 加密 / Mask 等方式保存和展示。

## 10.8 日志口径保持真实

没有真实数据就明确为 0 / 未接入，而不是用相近事件冒充。

最典型的是：

```text
提取IP ≠ 使用IP
```

## 10.9 数据过期不能继续显示健康

监控系统必须区分：

```text
健康
异常
离线
未知/过期
```

避免旧监控样本导致误判。

## 10.10 每个阶段都必须从空库跑 Flyway

M1–M8 一直坚持：

```text
新 PostgreSQL
→ 从 V1 开始迁移
→ 当前最新版本
→ 启动服务
→ 执行业务 Smoke Test
```

而不是只在开发者已有数据库上验证增量 SQL。

# 十三、结论

M1–M8 的本质不是连续增加八批页面，而是逐步把最初的产品原型演进为一套具备真实数据库、真实权限、真实业务状态、真实 API、真实日志、真实监控与自动化 CI 验收的工程。

其演进路径可以概括为：

```text
M1 先让系统真正跑起来
 ↓
M2 建公共系统底座
 ↓
M3 建客户主体
 ↓
M4 建资源底座
 ↓
M5 建产品能力
 ↓
M6 用订单和服务把客户、产品、资源串起来
 ↓
M7 让客户真正可以调用服务
 ↓
M8 让平台能够监控、告警、统计和运营
```

截至 M8，后续研发可以在一个相对稳定的业务基线上继续推进，而不需要再反复重建客户、资源、产品、订单、服务这些核心对象。
