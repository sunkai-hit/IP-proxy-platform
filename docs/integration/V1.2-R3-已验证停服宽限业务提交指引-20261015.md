# V1.2-R3 第七批｜已验证停服后的业务状态提交与IPv4宽限保留

> 阶段：**实现并待真实产品联调**。沿用 V1.2-R3 既定业务规则和第六批的 `svc_action_task` 任务/产品组证据；不修改V1～V27数据库迁移，不扩展新的代理产品范围。

## 1. 交付范围

- 实现 `ProductExpiryStopCommitter`：仅将 `STOP_FOR_GRACE` **真实执行且网络验证通过**的任务，事务化落账为当前服务 `EXPIRED / GRACE_HELD`。
- 管理接口：`POST /api/admin/v1/v12/delivery-actions/{operationKey}/commit-expiry-stop`，沿用业务平台`service:release`权限或超级管理员。
- 使用 `FOR UPDATE OF s,t` 锁服务和任务，严格匹配任务操作编号、远端编号、`SUCCEEDED`状态、`VERIFYING/NEEDS_BUSINESS_COMMIT`阶段、网络核验、原合同到期时间、宽限天数快照。已续费、原到期时间改变、服务状态改变、缺出网证据时全部拒绝提交。
- 核验`sampledAt/verifiedAt`，确保真实服务呈`STOPPED + VERIFIED`且停服证据晚于原到期时间；保留远端证明在`svc_action_task.result_summary`中。
- 只对 **当前服务ID** 执行 `svc_egress_claim.claim_status='GRACE_HELD'`并同步该服务原合同宽限截止，不按公网IPv4批量更新；长效共享出口其他客户完全不动。
- 冻结当前服务的平台凭证（`svc_credential`）；不删除服务、凭证、资源绑定、旧独享占用，也不写任何`RELEASED`状态。
- 任务落为`SUCCEEDED/BUSINESS_COMMITTED`，在结果摘要中记录提交人、时间和已变更业务状态，保留原始异步停服下发人；重复调用按幂等返回，不再重复执行。
- `grace_days_snapshot=0`也必须先真实停服；本批仍保留出口占用为`GRACE_HELD`，由独立的**真实释放验收**任务再释放回短效池，绝不因为0天宽限提前直接释放IPv4。

## 2. 允许提交的唯一流程

```text
已核实付款/原套餐权益 → 服务到期扫描登记 STOP_FOR_GRACE
  → 业务平台授权操作员持久化task/远端operationId
  → 产品组按服务级暂停（共享长效只停当前客户）
  → 产品组任务SUCCEEDED + 该服务STOPPED/VERIFIED
  → 产品组证明时间与合同到期匹配，业务操作人工审核
  → 事务提交：
      svc_instance.status=EXPIRED,expiry_phase=GRACE_HELD
      当前serviceId的svc_egress_claim=GRACE_HELD
      当前serviceId的svc_credential=FROZEN
      svc_action_task=SUCCEEDED/BUSINESS_COMMITTED
  → 固定IPv4继续占用，等待到宽限截止/真实释放任务
```

**不允许跳步**：`HTTP 202`、`SUCCEEDED`但无真实STOPPED、任务/服务到期时间不一致、未完成的历史IPv4占用迁移、无`svc_egress_claim`，均不能推进成功状态。不得由数据库状态修改触发未经批准的产品组实际停服。

## 3. 合同与共享规则

| 情况 | 应用结果 |
|---|---|
| 长效出口同时服务客户A、B，A到期已真实停服 | 仅A的服务和出口claim进入宽限；B的服务/凭证/claim不变 |
| 客户A在宽限期内续费且产品组真实恢复 | 续费仍按原到期时间顺延；不能复用旧停服回执造成二次停服 |
| 独享服务到期且套餐宽限N天 | 实际停服后固定IPv4保持全局排他到真实释放成功 |
| 套餐宽限为0 | 原到期即要求真实停服；之后受控释放，不能跳过真实释放 |
| 产品组超时、未知或验证时间不可信 | 保持服务及固定IP占用；任务待查单/人工处理 |
