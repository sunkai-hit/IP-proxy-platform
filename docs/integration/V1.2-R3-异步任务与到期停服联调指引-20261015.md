# V1.2-R3 第六批｜异步操作任务持久化、停服试运行与安全对账

> **研发联调框架，不代表产品组写接口已签收。** 本批沿用V22的 `svc_action_task`，没有新增表或修改V1～V27迁移。所有产品写操作默认禁用。需求仍以此前确认的V1.2-R3和双组接口联合评审稿为准。

## 1. 完成的工程能力

| 模块 | 已实现 | 禁止误解 |
|---|---|---|
| `ProductTaskReconciler` | 用 `remote_operation_id` 从产品组 `GET /product/v1/tasks/{operationId}` 查询，CAS写回既有任务表 | 不调用远端写接口；`SUCCEEDED`仍必须进行网络与业务双重验收 |
| `ProductGroupStopClient` | 候选 `POST /product/v1/services/{serviceId}/actions`，只支持 `PAUSE` 且必须返回匹配操作编号的HTTP 202受理回执 | 202不是停服成功；未接产品组前不可打开开关 |
| `ProductExpiryStopDispatcher` | 已到期长效/独享服务的STOP_FOR_GRACE任务：预检→抢占并持久化操作编号→下发单次请求→存储结果或不确定状态 | 不触发实际 `svc_instance.status` 或 `svc_egress_claim` 修改；未知结果不自动重发 |
| 两个操作员入口 | `POST /api/admin/v1/v12/delivery-actions/{operationKey}/dispatch-expiry-stop` 和 `.../{operationKey}/reconcile` | 需要业务平台 `service:release` 权限或超级管理员；不提供手工标成功功能 |

## 2. 双方接口配置

本次新增 `PRODUCT_GROUP_WRITES_ENABLED`，**默认 `false`**。启用前必须由两组人员审核接口路径、实际产品端配置、服务级停服含义、幂等保证与查单状态，并配置 `PRODUCT_GROUP_BASE_URL` 和 `PRODUCT_GROUP_API_TOKEN`（至少32字符，仅HTTPS或本机HTTP）。线上还须配置网络准入和密钥轮换，不能仅凭一个测试Bearer密钥上生产。

**停服必须是服务级授权停止：**长效共享同IPv4的其他客户不受影响，宽限期保留固定IPv4，不能对共享线路执行全局断网、拨号或直接回短效池。

## 3. V22任务状态推进

```text
到期任务扫描（现有）  PRECHECK_BLOCKED / WAITING_REAL_ADAPTER
   |
   | 产品组契约和管理员权限确认，写开关显式启用
   v
数据库原子抢占 + 持久化remote_operation_id -> RUNNING / DISPATCH_IN_FLIGHT
   |
   | 单次POST PAUSE，携带稳定operationId和X-Operation-Id
   |     ├── HTTP 202且accepted=true且ID一致 -> RUNNING / REMOTE_ACCEPTED
   |     └── 超时、响应歧义或非202 -> COMPENSATION_REQUIRED / DISPATCH_RESULT_UNCERTAIN
   v
管理员查单（GET产品组任务）：
   ACCEPTED/PENDING -> PENDING
   RUNNING -> RUNNING
   VERIFYING -> VERIFYING
   SUCCEEDED -> 实际服务状态、verifiedAt匹配后仍只标VERIFYING/NEEDS_BUSINESS_COMMIT
   FAILED/UNKNOWN/COMPENSATION_REQUIRED -> COMPENSATION_REQUIRED，禁止盲目重发
```

没有remote_operation_id的历史任务不会擅自下发；已终结的任务不会被重新拉回处理中。数据库更新用 `id + 原任务状态 + remote_operation_id` 防止并发任务互相覆盖。

## 4. 安全及验收边界

- 两个管理员入口均由业务平台审核`service:release`权限。操作员账号ID随任务抢占写入`actor_user_id`，任务操作有持久编号。
- 产品组202仅是异步受理，不会把业务订单或服务标记为已开通/已停服，也不会释放或复用IPv4。
- 超时后必须**使用原remote_operation_id查询**。如果程序在“标记已发”之后崩溃，这个编号已持久化，不能再用新编号重发。
- `SUCCEEDED`也要求单独 `GET /product/v1/services/{id}` 确认正确的实际RUNNING/STOPPED及`verificationStatus=VERIFIED`、`verifiedAt`；再由将来经业务评审的状态提交器落账。**本批尚未实现业务状态自动提交。**
- 对于`RELEASE`和`TERMINATE`，即使服务显示STOPPED也无法证明独享IPv4已释放；需产品组额外出口/授权排他回执。**本批不发送真实释放操作。**
- 既有CI继续使用`m6-mock`模拟环境做工程烟测；产品组真实网络联调尚未发生。

## 5. 接下来仅需收敛的依赖

1. 产品组签收`POST /product/v1/services/{id}/actions`和`GET /product/v1/tasks/{operationId}`的版本、回执与同operationId幂等语义；联调实际共享长效停服不会影响其他客户。
2. 对账结果达到`NEEDS_BUSINESS_COMMIT`后，完成业务服务状态/宽限/出口占用的**可重放、按事务提交的状态收敛器**，附真实网络证据；不得凭202提交。
3. 基于同一任务机制逐项扩展短效→长效/独享资源转换、VPN与隧道等已确认动作；先验收一条端到端链路后再批量复用。
